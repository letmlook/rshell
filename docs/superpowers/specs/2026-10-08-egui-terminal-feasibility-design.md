# egui 纯 Rust 终端可行性验证设计

更新：2026-10-08。

## 目标

用一个与现有 Tauri/Vue 产品入口隔离的原生实验程序，验证 RShell 的终端界面能否改为 `eframe`/`egui` + Rust VT 状态机。实验回答的是技术可行性，不建立新的生产 UI，也不连接真实 SSH 服务。

成功意味着以下闭环均能在一个可运行程序中观察：终端字节进入 VT 状态机；状态机产生可绘制网格；egui 正确显示文本、基础样式和光标；用户输入可转换为终端字节；滚动、选区、复制粘贴和尺寸变化可以工作。

## 方案选择

采用 `alacritty_terminal` 作为 VT/ANSI 状态机，使用 `eframe` 承载原生窗口，并由自定义 egui 画布读取终端网格进行绘制。

选择该方案是因为它最接近正式迁移所需的结构：终端仿真与 UI 绘制分离，后续可以把演示字节源替换成现有 `TerminalService` 的输出通道。`vt100` 路线实现更快，但不足以验证复杂终端状态和历史缓冲；保留 xterm.js 的 WebView 路线不满足纯 Rust 目标。

## 范围

实验验证：

- eframe 原生窗口可以在当前 Rust workspace 中独立构建和启动。
- 字节流驱动 VT/ANSI 状态机，并持续触发 egui 重绘。
- 终端画布显示 ASCII、中文或其他宽字符、基础 ANSI 色、256 色、前景和背景、光标与清屏/定位结果。
- 键盘的普通字符、Enter、Backspace、Tab、方向键和常用 Ctrl 组合能编码成终端输入字节。
- 鼠标滚轮浏览历史，鼠标拖动建立选区，复制选区和粘贴剪贴板文本可观察。
- 画布尺寸变化能稳定换算为终端列数和行数，并把新尺寸应用到状态机。
- 调试状态区显示当前 rows/cols、输入字节、滚动位置和最近一次解析/绘制状态。

实验不验证：

- SSH、Telnet、Serial 或本地 PTY 的真实连接。
- SFTP、隧道、密钥、自动化、插件或完整工作区布局。
- Tauri 到 egui 的生产迁移与配置兼容。
- 完整 xterm.js 行为一致性、无障碍能力或最终视觉质量。
- 性能优化和发布包构建。

## 代码位置与隔离

新增 workspace crate：`src-tauri/crates/egui-terminal-prototype/`。crate 名称和界面内均标注 `PROTOTYPE`，不加入现有 `rshell` 二进制的依赖，不修改 Tauri 启动入口，不复用生产配置文件，也不持久化状态。

该 crate 加入现有 Cargo workspace，以便共享工具链和锁文件。运行入口为：

```bash
cargo run --manifest-path src-tauri/Cargo.toml -p egui-terminal-prototype
```

## 组件

### 演示字节源

后台任务按顺序发送固定场景：普通文本、SGR 样式、16/256 色、光标移动、局部覆盖、清屏、宽字符、换行滚动和分片输入。场景可以从界面重新播放，并可以暂停持续输出。

固定输入使失败可重复，避免把网络和认证问题混入终端验证。

### 终端模型

终端模型封装 `alacritty_terminal` 状态与 ANSI processor，只暴露以下能力：

- 写入字节；
- 调整 rows/cols；
- 读取当前可见网格和历史位置；
- 设置滚动位置；
- 按网格坐标维护实验用选区；
- 输出选区文本。

该边界用于确认将来可以把状态机和绘制器分别替换，而不把 egui 事件处理混入 VT 解析。

### egui 终端画布

画布采用固定宽度字体，根据可用矩形和字符尺寸计算 rows/cols。每帧读取可见单元格，合并相同样式的连续内容后绘制背景和文本，再绘制光标与选区覆盖层。

输入由具有焦点的画布接收。普通文本使用 egui 文本事件；控制键和导航键显式映射为字节序列。鼠标坐标换算为网格坐标，用于拖选和滚动。

### 调试状态区

状态区显示终端尺寸、可见行范围、累计输入/输出字节、最后一次键盘编码，以及能力检查结果。它用于提供可检查证据，不作为未来产品界面的设计。

## 数据流

```text
演示任务 -> mpsc<Vec<u8>> -> VT processor -> terminal grid
                                              |
                                              v
用户输入 <- 输入编码器 <- egui terminal canvas -> egui painter
                              |
                              +-> resize(rows, cols)
                              +-> selection / scroll / clipboard
```

后台任务只发送字节，不直接访问 egui 或终端模型。主 UI 线程在每次更新时排空有界数量的消息，推进状态机并请求下一次重绘，防止持续输出让单帧无限工作。

## 错误与限制呈现

启动失败直接返回错误。字体加载、剪贴板和不支持的输入事件在状态区显示具体失败或缺失能力。无法正确呈现的单元格以替代字符显示，并记录计数，避免悄悄判定成功。

实验允许使用简化的选择语义，但必须标记跨行复制、宽字符命中和组合字符的实际结果。任何崩溃、状态机 API 无法稳定读取网格、宽字符导致坐标错位，或终端更新显著阻塞 UI，都记为迁移风险。

## 验证方法

本轮验证执行：

1. workspace 编译检查，证明 eframe、egui 和终端状态机依赖可以共存。
2. 启动实验窗口，逐项操作内置场景、键盘输入、滚动、拖选、复制粘贴和窗口 resize。
3. 记录观察到的行为和未覆盖能力。

不为 throwaway prototype 建立完整测试套件。可以添加最小模型断言，只用于证明 ANSI 分片输入和 resize 不破坏状态。

## 判定标准

结论分为三类：

- **通过**：核心闭环可用，发现的问题可以在正式实现中逐步补齐，不影响选择 egui。
- **有条件通过**：基本闭环可用，但宽字符、选区、输入法、性能或平台行为中存在需要第二个专项验证的问题。
- **不通过**：终端核心难以安全读取/绘制、交互无法满足终端使用要求，或当前依赖组合无法可靠构建运行。

最终记录必须把内容分成“已验证”“尚未验证”“阻断项/后续专项”，不能用成功启动窗口代替终端能力验证。
